# src/core: what every game shares

Core is the part of Ember Vault that doesn't know which game you play. It may import `obsidian`, other core modules, and the contract/registry types (`../systems/contract`, `../systems/registry`). **It must not import any game system or `src/app`;** `npm run lint` fails if it does.

## When code belongs here

When a **second** game needs it. Don't move code into core because it might be shared one day: move it when a system would otherwise copy it, and make the first system use the core version too (as was done for the hover card and inline references). Copying a module from one system into another is the thing to avoid.

## Reaching a game system from core

Core gets the plugin as a type (`import type EmberVaultPlugin from '../../main'`) and asks it:

- `plugin.system(path?)`: the `GameSystem` for a note. It resolves the note's campaign, else the active campaign, else the default (Nimble).
- `plugin.edition(path?)`: the rules version, for systems that have several.
- `plugin.systems`: the registry (every shipped system).

Core tells systems what happened through `plugin.events`: `party-changed` (the party was edited or swapped) and `active-campaign-changed`. Each campaign keeps its own party and, through `GameSystem.campaignState`, each game's fight (`settings.campaigns[folder].games`); `CampaignStore.setActive` swaps both. Systems listen in their `register()`.

Then it calls a contract member: `system.characters?.promptNew(…)`, `system.quickLook(…)`, `system.conditions(edition)`. If what you need isn't in the contract, add it there (see [src/systems/AGENTS.md](../systems/AGENTS.md)). Core never reaches into a game's state (`nimble()`, `dnd5e()`, `plugin.runtime(id)`); ask through the contract.

## Timed conditions (`tracker/effects.ts`)

A condition's timing lives on core's `AppliedCondition` as optional fields (`ConditionTiming` in `types.ts`), so fights saved before load as they were: `rounds` alone still counts down at the end of its bearer's turn.

- `rounds`, `ends` (`'start'`, or missing for the end), `whose` (`'source'` with `sourceId`/`sourceLabel`, or missing for its bearer), `triggers` (`EffectTrigger[]`: `damage` with `dice`/`damageType`, `save` with `ability`/`dc`/`endsOnSave`, `reminder` with `text`, each `at` the start or end of the bearer's turn). `tickedRound` and `fired` are the engine's own marks.
- **The one call:** `turnEvent(bearers, { combatantId, when: 'start' | 'end', round })` at every turn boundary. It counts down what counts on that turn (once a round), ends what runs out, and returns `{ ticked, expired, prompts }`. Bearers are `{ id, conditions, out? }` (`out`: takes no turns, so conditions it caused count on their bearer's turn). It changes conditions in place.
- **The rules it keeps:** at a start, what ends there ends before its effects; at an end, effects first. A save that would only end a condition that's ending anyway isn't asked. Effects fire once per round and boundary, so Back/Next or a turn toggled twice never asks twice. Put on during the turn it counts on, a condition skips that turn's end ("until the end of its next turn").
- **Back:** keep the `TurnEventResult` of the last step and call `undoTurnEvent(bearers, result)`: counts go back up and conditions that ran out come back, keeping what the GM changed since.
- **Applying:** `applyTiming(name, timing, { bearerId, turn, source, value })` writes only what differs from a plain condition; `retime` changes one in place; `cleanTiming` reads timing from data.json defensively; `customDef` and `keepCustomCondition` save a custom condition with its timing (`settings.customConditions`, every game).
- **A tracker using it:** call `turnEvent` where its turns start and end (5e: `nextTurn`/`startCombat` in `dnd5e/combat.ts`; Nimble: a side's turn starting, a turn marked done, the round ending, in `nimble/encounters.ts`), open `openConditionPicker`/`openConditionDetails` with the game's words (abilities, damage types) and its store's add/update/remove, and pass the prompts to `showEffectPrompts` with handlers that apply damage by the game's HP rules and know a save's bonus.
- **Presets:** a game's `conditions(edition)` can carry `timing` on a `ConditionDef` (5e 2024's Burning). The conformance suite checks it's in the form `cleanTiming` keeps.

## Pitfalls

- **Campaigns are indexed after Obsidian's layout is ready.** Anything drawn at startup that depends on the note's system or edition must redraw on `plugin.campaigns.on('changed')` if the answer changed (see `app/encounter-blocks.ts`).
- **`title` attributes become Obsidian tooltips:** `tooltips.ts` moves them to `aria-label`. Tests should read either.
- **Names in frontmatter can be numbers** (`edition: 2024` is a YAML number); read them through helpers that accept both.
- **Pure modules** (`types.ts`, `tracker/effects.ts`, `tracker/hp.ts`, `note-kinds.ts`, `spotlight-def.ts`, `spotlight-source.ts` (types only from obsidian), `compendium/query.ts`, `content/spec.ts`, `content/packs.ts`, `content/blocks.ts`, `yaml-lite.ts`, `encounter-def.ts`, `map-def.ts`, `markdown.ts`, `dice.ts`, `campaign-model.ts`, `npc-lookup.ts`, `link-rename.ts`) must not import `obsidian`.

## Your own content (`content/blocks.ts`, `store.ts`, `new-entry.ts`)

- **A game opts in** with `content.blocks` (`{ prefix, folder, kinds }`: ```<prefix>-<kind> fences, notes under `<content folder>/<folder>/<kind plural>/`) and `content.card` (draws a block's entry, which may hold only the fields that checked out). Kinds that already have their own block (spells, items, monsters) aren't listed; never add a fence that clashes with an existing one.
- **Where entries join:** the store reads every note in the content folder and hands each game its blocks' entries as one more `LoadedPack`, named Homebrew (`homebrew: true`, each entry with its `file`), after the file packs, from `plugin.content.enabled(id, path)`. A game that already takes packs needs nothing more; it should tag entries with a `note` as Homebrew and offer Open note. The pack object stays the same until a note changes, so a layer can compare by identity.
- **New on a tab:** call `newContent(plugin, system, kinds, ev)` with the kinds the tab makes, and `newButtonLabel` for the button. **The seam for guided builders:** register a builder kind with the same id (`registerKind(system, 'class', …)`, not hidden) and New opens it instead of writing a starter; have its `output().folder` be `contentFolderFor(plugin, system, kind)` so what it writes joins the compendium. Give it a `group` (Nimble's are `hero`) so the builder's kind bar shows a hero's content apart from monsters, spells and items. **The Edit pencil on a block:** the game's `content.editSeed({ kind, value })` returns the seed its builder opens on (Nimble: `{ entry, editing: true }`); blocks-ui.ts adds the pencil when there's a builder and a seed, and Save rewrites the block in place (asking first when it would drop lines or fields it couldn't read).
